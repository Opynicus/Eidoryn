# 倒带内存与捕获基准

`examples/rewind_bench.rs` 用于比较完整运行时快照的捕获成本与保留内存，不需要 BIOS、游戏镜像或桌面界面。使用 release 构建、解释器和串行渲染器，连接两张格式化的 128 KiB 记忆卡；Linux 下从 `/proc/self/smaps_rollup` 读取整个进程的 RSS 和 PSS。

## 复现方法

先构建，再直接运行二进制，避免比较期间源码变化触发重新编译：

```sh
cargo build --locked --release --no-default-features --example rewind_bench
target/release/examples/rewind_bench 0
target/release/examples/rewind_bench 20
target/release/examples/rewind_bench 40
```

每个条件应启动独立进程，重复五轮，并在相邻轮次反转 `0、20、40` 的执行顺序，以降低运行顺序对结果的影响。跨版本比较时保留两个版本各自编译的二进制，在每个条件内交错执行新旧版本，并轮换哪个版本先运行；使用相同机器、编译参数和操作系统，等待其他编译、测试等 CPU 负载结束后再测量。

输出是一行 CSV，字段依次为：

```text
mode,count,rss_before_kib,rss_after_kib,pss_before_kib,pss_after_kib,estimated_bytes,capture_mean_us,capture_median_us,capture_p95_us,capture_max_us,capture_total_us,wall_ms,guest_seconds,history_seconds,advanced_frames,final_cycles
```

基准先执行内置 demo 的十个帧，再执行相同的四十个帧，分别保留最后 0、20、40 份快照。每次捕获之间都执行真实客体指令，并验证模拟周期和客体写入的帧计数递增；每个执行切片后排空音频，与无音频输出的工作线程一致。所有快照在内存采样结束前保持存活。

默认 `frame` 模式是固定数量微基准。内置 demo 的帧不等待 VBlank，因此这些快照不能解释为 5 秒或 10 秒游玩历史；输出中的 `guest_seconds` 和 `history_seconds` 是实际客体周期换算的秒数。可选第二参数 `250ms` 会让相邻采样至少间隔 250 毫秒客体时间，但 demo 在此期间会生成大量帧，运行时间会显著增加。不同采样模式的结果应分开比较。

0 份快照是不记录倒带的对照组，执行相同客体工作。40 份条件刻意绕过工作线程的 256 MiB 估算预算，用于比较每份快照的成本；实际工作线程会按预算和设定时长淘汰历史。

`estimated_bytes` 是 `RewindState::memory_size()` 的保守预算估算，不是实测堆分配。RSS/PSS 包含整个进程，应同时比较关闭倒带的对照组。捕获耗时包含 `rewind_state()` 内的克隆、GPU 同步和内存估算，不包含前向模拟、历史队列操作或 UI；分配器复用和系统负载仍会影响结果。

## 同轮交错结果

2026-11-15，比较功能提交 `43317b42d83163dd89c0b085850c6afcfb2f7b78` 与本分支的 BIOS/记忆卡共享、直接内存估算实现。环境为 AMD Ryzen 9 8945H、Linux x86-64、Rust 1.100.0、release + thin LTO，核心默认特性关闭。两版均由同一 `/tmp` 独立 Cargo 项目直接依赖各自核心，使用相同基准主体编译，并将完成的二进制各自复制到独立路径；后续源码修改不会影响已保存的二进制。基线核心源码 SHA-256 已与功能提交逐文件核对一致。

完成其他编译和测试后，在每轮、每个快照数量下交错运行两个二进制，共五轮。内存净增量先在每个进程内计算 `after - before`，再取五轮中位数；RSS/PSS 含分配器及进程开销，因此保留 0 份的对照组也列出。

| 保留快照 | 原 RSS 净增 (MiB) | 新 RSS 净增 (MiB) | 原 PSS 净增 (MiB) | 新 PSS 净增 (MiB) |
| --- | ---: | ---: | ---: | ---: |
| 0 | 0.285 | 0.066 | 0.219 | 0.000 |
| 20 | 91.918 | 74.270 | 91.852 | 74.203 |
| 40 | 183.434 | 148.957 | 183.363 | 148.891 |

捕获延迟分别取每轮平均耗时与每轮 p95 的中位数。每轮只有 20 或 40 次捕获，尾延迟仍有较明显的测量波动。

| 保留快照 | 原平均 (ms/次) | 新平均 (ms/次) | 原 p95 (ms) | 新 p95 (ms) |
| --- | ---: | ---: | ---: | ---: |
| 20 | 2.711 | 1.889 | 3.816 | 3.715 |
| 40 | 2.611 | 1.719 | 4.308 | 2.953 |

在此场景中，20/40 份历史的 RSS 净增量分别下降 19.2%/18.8%，平均捕获延迟分别下降 30.3%/34.1%。预算估算从 180.508/361.015 MiB 变为 180.211/360.423 MiB；固定份数基准不会因预算微调而少保存快照，内存收益不能归因于提前淘汰。

所有条件都推进四十个帧、0.000290533 客体秒，最终周期均为 12319。20/40 份历史的实际跨度分别为 0.000138003/0.000283270 客体秒。该结果只说明此 demo 状态下的完整快照成本，不能据此推断商业游戏的可回退时长或帧率。
