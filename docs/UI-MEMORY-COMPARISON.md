# UI 重构前后的内存对比

在本机相同窗口、英文、Release、软件渲染条件下，没有复现明显的进程 RSS 增长：重构前约 **88.27 MiB**，当前约 **88.44 MiB**。当前中文界面约 **93.20 MiB**，其中新增 CJK 字体文件的驻留页约 **4.75 MiB**。普通开发构建也有更大的程序文件驻留开销，下面单独列出。

这些是内置原创演示的测量，不是所有游戏、显示器或运行配置的结论。不能把累计分配量、虚拟映射大小和 GPU 内存直接当作进程 RSS。

## 版本与测量条件

| 版本 | 标识 | 说明 |
| --- | --- | --- |
| 重构前 | `feature/device-event-boundaries` / `e0fc3ab` | 本次要求的基线 |
| 重构合并版 | `68face3` | 已经包含 UI 重构和 i18n |
| 当前优化版 | `7b17106` | 字体请求复用和静态侧栏缓存 |

基线的代码树与 `e2e64ec` 完全一致；重构合并版的代码树与 `719bcbf` 完全一致。本次使用从这两个等价代码树构建的二进制，记录了代码树 ID 和二进制 SHA-256。上一份 [UI 内存测量](UI-MEMORY.md) 只比较重构合并版与优化版，没有测量重构前的工程；本报告补齐这个基线。

环境为 AMD Ryzen 9 8945H、Linux 7.3.1、Niri 26.04、Rust 1.98.1、GPUI 0.2.2，150% 显示缩放，1280×900 逻辑像素窗口。固定 Midnight、串行软件渲染、CRT 关闭、静音、无记忆卡文件，使用独立临时配置，不加载 BIOS 或光盘。

原生 RSS 使用默认分配器。堆分析另启进程注入 gperftools，比较启动预热后两份约间隔 5 秒的快照。英文每版本重复三次，中文每版本有两次有效重复；失去焦点的采集被排除，没有混入中位数。后面的开发构建与一分钟观察各为独立单次运行，允许窗口失焦并记录焦点，只用于内存诊断。核验时发现共用 Cargo 目标目录导致开发版复用了旧主题常量；受影响样本已排除，在重建 host crate、校验主题常量后重新采集。独立保存的 Release 二进制及其样本不受影响。

## Release 对比

| 版本 / 语言 | 原生 RSS 中位数（MiB） | 范围（MiB） | 分析器中的存活堆（MiB） |
| --- | ---: | ---: | ---: |
| 重构前 / English | 88.27 | 87.75–88.30 | 24.41 |
| 重构合并版 / English | 88.07 | 86.29–88.61 | 23.14 |
| 当前 / English | 88.44 | 88.19–88.80 | 22.96 |
| 重构合并版 / 简体中文 | 93.34 | 93.33–93.35 | 23.40 |
| 当前 / 简体中文 | 93.20 | 93.16–93.23 | 23.25 |

存活堆是请求字节数，不包含字体文件映射、分配器空闲页、程序/共享库驻留页和完整 GPU 内存。它与 RSS 来自不同进程，不能直接相减作为“非 UI 内存”。

## 找到的增长来源

### 1. 中文界面需要额外的 CJK 字体

重构前只有英文；新增的 [语言选择](../src/i18n.rs) 和 [启动设置](../src/desktop/settings.rs) 支持中文，并可根据保存的设置或系统语言选择中文。

本机中文文本触发 `NotoSansCJK-Regular.ttc` 的按需映射。与旧英文界面相比：

- 该字体额外贡献 **4.75 MiB RSS**，解释了约 4.93 MiB 总 RSS 差异的大部分。
- 字体文件总虚拟映射从约 **1.71 MiB** 变成 **20.30 MiB**；约 18.59 MiB 的映射增长不等于同样大小的物理内存增长。
- 字体文件实际 RSS 合计约从 **0.77 MiB** 变成 **5.55 MiB**；中文还需要额外的字形与文本排版缓存。

切回英文启动的受控对照中没有 CJK 字体映射。这里没有发现所有语言字体被提前完整复制到堆上的证据；翻译字符串本身是静态字符串，也没有每帧解析语言文件。

### 2. 更多 UI 绘制与交互代码增加程序驻留页

`smaps` 中可执行文件映射的驻留量中位数：旧版 **16.27 MiB**，当前英文 **17.10 MiB**，当前中文 **17.27 MiB**。这部分包含代码和只读数据，不能简单归为 SVG 或布局对象。

普通 `cargo build --locked --offline --bin eidoryn` 的开发构建也做了补充观察（各一次，10 秒时）：

| 开发构建 | 总 RSS（MiB） | 程序文件映射 RSS（MiB） |
| --- | ---: | ---: |
| 重构前 / English | 114.85 | 42.17 |
| 当前 / English | 117.77 | 44.11 |
| 当前 / 简体中文 | 121.29 | 44.32 |

英文开发构建增加约 **2.93 MiB**，其中程序文件映射增加约 **1.94 MiB**。因此不能拿旧版 Release 与新版普通 `cargo run` 的内存直接比较。工程的开发配置已是 `debug = 0`，这个差异不能简单解释为“多了调试符号”。这组样本数较少，数值用于定位，不能视为跨机器的固定增量。

### 3. 布局临时分配确实更多，但存活堆没有同幅增长

按调用栈归因的存活堆中位数（KiB）：

| 部分 | 重构前英文 | 重构合并版英文 | 当前英文 | 当前中文 |
| --- | ---: | ---: | ---: | ---: |
| SVG 路径 | 0.59 | 0.59 | 0.59 | 0.59 |
| 字体/文本 | 977.90 | 1,202.27 | 857.78 | 1,355.17 |
| 布局/元素 | 2,925.09 | 1,965.40 | 2,089.96 | 2,089.98 |
| 共享图集/场景 CPU 缓冲 | 1,450.35 | 1,018.52 | 1,054.68 | 738.37 |

旧界面默认同时展示寄存器和反汇编；新 Console 将这些移到了独立调试器。新版布局层次和交互状态增加了逐帧临时工作，但这不代表更多对象一直存活。

英文布局/元素分配率约为 **98.02 → 127.75 → 113.54 MiB/s**（旧版、重构版、当前）。全进程分配率则约为 **199.78 → 191.68 → 163.80 MiB/s**，因为字体查找错误等重复工作减少了。分配率衡量反复申请和释放的压力，不能当作每秒新增常驻内存。

当前侧栏缓存比未优化的重构版多保留了一部分元素状态；这是已经量化的空间与逐帧工作量权衡，没有形成按帧累计的缓存条目。

## 排查后未发现的原因

- **CPU、GPU、JIT 核心变大**：与基线相比，`crates/ps1`、`crates/jit-runtime` 没有修改。host 层只有主题颜色调整。Runner 的运行状态/渲染器版本字段是少量固定状态，未增加大容量资源缓冲。
- **新增大型默认依赖**：两版默认构建的普通依赖包集合相同。锁文件增加的部分包来自可选 `ui-tests`，不能仅凭 `Cargo.lock` 变长就判断运行时占用增长。
- **SVG 每帧重新加载**：16 个源码总计 3,619 字节，借用静态字节；稳态没有新增 SVG 解析/栅格化分配。表中 0.59 KiB 含 GPUI 原本就创建的 SVG renderer 状态，不是图标的全部 GPU 成本。当前图标不含 SVG 文本，不触发另一份 SVG 系统字体库。
- **Logo 变大**：两版使用同一个 1254×1254 PNG，构造方式相同。它本身有解码和纹理成本，但不是本次重构新增的资源。

## 较长运行与 GPU 观察

独立原生 Release 进程在第 5、10、60 秒采样：

| 版本 | 5 秒 RSS | 10 秒 RSS | 60 秒 RSS |
| --- | ---: | ---: | ---: |
| 重构前英文 | 88.375 MiB | 88.375 MiB | 88.602 MiB |
| 当前中文 | 92.828 MiB | 92.828 MiB | 93.055 MiB |

两者都是约 **232 KiB** 的增量，没有观察到新版独有的持续增长。这只有一分钟和三个采样点，不能据此证明所有游戏、长期运行或反复切换设置都不存在泄漏。

同两次运行中，按唯一 DRM client 去重后的 GPU GTT + VRAM 记账分别约 **199.10 MiB**、**198.93 MiB**，三个采样点保持不变。其余开发构建探测中显存池大小和 VRAM/GTT 分布有所波动，不能把单次 VRAM 增长归因于 UI 资源。该记账会包含共享/导入缓冲，也不能直接加到 RSS 上。即使 PS1 选择串行软件渲染，GPUI 仍使用 GPU 绘制窗口；这项共同开销在重构前已经存在。

## 复现与数据

[逐次数据](benchmarks/ui-memory-baseline-2026-11-12.json) 包含有效样本、内存分项、时间间隔、焦点条件、代码树和二进制摘要；没有包含 BIOS、游戏、存档或本机原始路径。

对两个独立 checkout 分别执行相同的 `cargo build --locked --release --bin eidoryn`，使用各自的目标目录、保留各自的二进制，再使用当前测量脚本。不要让两个版本共用 `CARGO_TARGET_DIR`，避免路径依赖的旧产物影响版本核验。旧版没有 `--language`，用 `--legacy-ui`：

```bash
python3 scripts/profile_ui_memory.py capture \
  --binary /tmp/eidoryn-before --output /tmp/eidoryn-before-rss \
  --legacy-ui --niri --rss-only

python3 scripts/profile_ui_memory.py capture \
  --binary /tmp/eidoryn-current --output /tmp/eidoryn-current-rss \
  --language en --niri --rss-only
```

中文改为 `--language zh-CN`。去掉 `--rss-only` 后可按 [原测量说明](UI-MEMORY.md#复现) 生成和分析堆快照。开发构建不加 `--release`，其结果单独统计。每次使用新输出目录；`--niri` 的正式比较要求采样时仍聚焦，操作其他窗口导致的失败样本应排除。

如果实际观察的是数十或数百 MiB 的额外增长，这次固定负载没有复现。继续定位应使用当时的启动命令、窗口尺寸/缩放、页面、语言、CRT、渲染器、游戏和观察时刻；新版会恢复保存的渲染器/CRT 设置，这也可能让表面上相同的启动命令运行不同配置。现有证据不支持通过删除 SVG、取消中文或移除正常缓存来解决一个尚未复现的大幅增长。
